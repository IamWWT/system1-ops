# 质量门禁

## 三层门禁（按节奏切）

### L1 — 每次提交（Commit）

| 检查项 | 如何验证 |
|--------|---------|
| 格式/lint 通过 | 语言对应 lint 命令（见 languages/） |
| 受影响模块单测通过 | 测试命令 |
| 无硬编码密钥/IP/端口 | `rg -n "(password|secret|api[_-]?key)\s*[:=]\s*[\"'][^\"']+"` 抽查 + 代码审查 |
| 无调试残留（print/console.log/todo 泛滥） | 审查 |
| FILE_INDEX 已同步 | `scripts/doc-check.sh` |

### L2 — 每个功能/里程碑

| 检查项 | 如何验证 |
|--------|---------|
| 集成测试通过（真实依赖） | 集成测试命令 |
| 进度日志已写（含失败） | `docs/04-progress/` 最新日期存在 |
| 文档与实现一致 | 文档宣称的功能都能指到代码/测试 |
| 契约未被破坏 | 检查接口签名变更是否影响消费方 |
| 错误路径已处理 | 代码审查（超时/异常/空值） |

### L3 — 交付/发布前

| 检查项 | 如何验证 |
|--------|---------|
| 全量 build + test + doc-check 绿 | `scripts/quality-gate.sh` |
| 安全清单过完 | standards/security.md 每项勾选 |
| 可靠性清单过完 | standards/reliability.md 每项勾选 |
| 关键路径性能有基准或明确"未测" | 基准输出落 docs/05-testing/ |
| 可观测性接入 | 结构化日志 + 健康检查（大型服务加指标/追踪） |
| 交付总结含已知限制 | README 或交付说明 |

## 阶段门禁（门禁 1–5，按研发阶段切）

> L1/L2/L3 是**按节奏**切（每次提交/里程碑/交付）；本节是**按研发阶段**切。
> 两套同时生效，不互相替代。核心思想：**质量是做出来的，不是测出来的**——
> 在关键环节设检查点，尽量把问题拦在注入它的那一阶段。

| 门禁 | 设在哪个阶段 | 检查什么 | 落在框架哪个 Gate | 工具化要求 |
|---|---|---|---|---|
| **门禁 1** | 开发起点 | **分支策略**：主干开发 → 特性分支开发 | Gate 2 → Gate 3 之间 | 分支保护规则 |
| **门禁 2** | 集成 | 代码扫描、**制品晋级**、流水线运行 | **Gate 3**（实现通过） | CI 流水线必跑；扫描不通过不许晋级 |
| **门禁 3** | 测试前段 | **单元测试 → 组件测试 → 组件集成测试**；指标建设 | Gate 3 → **Gate 4** | 测试命令退出码即门禁 |
| **门禁 4** | 测试后段 | 覆盖率分析、功能稳定性测试、**偏离度监控**、关键质量活动全景数据 | **Gate 4**（测试通过） | 指标可视化 + 阈值告警 |
| **门禁 5** | 投产前 | **防前序阶段注入的质量问题漏到投产/生产运行** | **Gate 5**（交付通过） | 投产前检查清单不可跳 |

**强制条款**：

1. **门禁可裁剪，不可省略**：小项目可把门禁 2–4 合并进一次 CI 运行，但**检查项一条不能少**；
   确实不做的必须写明"未做 + 理由 + 风险"。
2. **工具自动化形成强约束**：能由流水线判定的**必须**由流水线判定，
   禁止靠"我记得跑过了"（人的自觉不是门禁）。
3. **门禁 5 的判定对象是"前序阶段"**：投产前发现的问题要回溯**它是哪个阶段注入的**，
   并在复盘里给出"下次在哪道门禁拦住"的改进项——否则同类问题会再来一次。
4. 门禁结论写入进度真源（配合 process.md §9 Gate Review 清单）。

## 度量：最小指标集（看什么、何时看、超了怎么办）

> 企业级度量体系面向千人组织（统一数据管理/加权模型/分层视图）——个人与小团队
> 用**最小指标集**：每阶段只看几项真正有用的数字，**带阈值、带动作**。
> 原则：**指标没有触发动作 = 不采**（不产行动的仪表盘是装饰）。

### 何时看什么（按阶段选 ≤10 项）

| 阶段 | 指标（示例） | 阈值示例 | 超标时做什么 |
|---|---|---|---|
| **开发期**（L1/门禁 1–2） | 单测通过率、lint 通过率、新增覆盖率 | 通过率 100%；覆盖率不降 | 失败即挡在流水线；覆盖率下降 → 补测或写理由 |
| **集成期**（门禁 2–3） | 构建成功率、制品晋级成功率、依赖漏洞数 | 构建失败 0 容忍；漏洞按严重级 | 失败即停；高危漏洞 → 阻断晋级 |
| **测试期**（门禁 3–4） | 功能测试通过率、缺陷逃逸率、覆盖率门槛 | 通过率 100%；逃逸率 ≤5% | 逃逸超标 → 回溯哪个测试环节漏的（门禁 5 思想前置） |
| **交付期**（L3/门禁 5） | **交付周期、部署频率、变更失败率、恢复时间**（DORA 四件套） | 变更失败率 ≤15%；恢复 < 1 天 | 失败率升 → 查变更管理（change-management.md）是否在失效 |
| **运行期**（生产） | 可用性、错误率、响应时间 P50/P95/P99、TPS、资源占用 | 见 non-functional.md 各维度 | 触发告警 → 走应急流程（可观测性见 observability.md） |

### 强制条款

1. **最小集**：每阶段指标 ≤ 10 项；多于 10 项必须砍（砍不掉 = 说明你有专职度量团队）。
2. **四项一数**：每个指标必须写清——**定义 / 怎么采 / 阈值 / 超标动作**。
   写不出"超标动作"的指标直接删。
3. **偏离度监控**：指标连续两轮超阈值 → 写进进度日志，并触发对应门禁复查
   （门禁 4 的"偏离度监控"就是这个意思，不是堆仪表盘）。
4. 指标数据**必须真实**：禁止"凭感觉估数"；采不到就标"未采 + 原因"，不许编。

## Definition of Done（功能级）

一个功能"完成"必须同时满足：

1. 验收标准（PRD 中写的）有测试覆盖并通过；
2. 失败路径有测试（错误输入、超时、异常）；
3. 文档同步（FILE_INDEX/MEMORY/进度）；
4. 没有留下 TODO 冒充完成（TODO 必须注明责任人+日期，或移除）；
5. 宣称的能力与代码一致。
