# 非功能规范（Non-Functional Requirements & Testing）

> 版本: 1.0.0 | 状态: active | 适用范围: 分析/设计/测试/部署
> 定义：把"功能能跑"提升到"**在压力与故障下仍可用**"。
> 本规范补 `performance.md`（怎么保证性能）与 `reliability.md`（超时/重试/幂等）之缺口：
> **非功能需求怎么识别、怎么按架构分层注入故障、怎么收敛**。

---

## 1. 非功能需求基线（维度清单）

非功能需求**必须在需求阶段显式识别**，不能等测试阶段才发现。

| 维度 | 要回答的问题 | 典型指标 |
|---|---|---|
| **性能** | 多快？多少并发？ | 响应时间（P50/P95/P99）、TPS、并发数、吞吐量 |
| **容量/扩展** | 能装多少？怎么扩？ | 数据量、连接数、存储上限、横向扩展能力 |
| **可用性** | 允许停多久？ | 可用性等级（如 99.9%）、RTO、RPO、MTBF |
| **可靠性** | 出错会怎样？ | 错误率、数据一致性、事务完整性、幂等性 |
| **可维护** | 出问题好不好查？ | 日志完整性、可观测性、可诊断性 |
| **兼容/可移植** | 换环境还行吗？ | 多环境一致、版本兼容、浏览器/OS 支持 |
| **易用性** | 人用起来顺吗？ | 交互流程、错误提示可读性、多语言 |
| **安全/合规** | 会不会出事？ | 见 `security.md`（认证/授权/脱敏/审计） |
| **资源占用** | 吃多少资源？ | CPU/内存/磁盘/网络基线 |
| **计量准确性** | 数准不准？ | 精度、误差控制、对账能力 |

**强制条款**：

1. **每个项目必须产出非功能需求清单**（可并入 BRD 的"非功能需求"章节），逐条给**可验证指标**；
   写不出指标的维度标注"不适用 + 理由"，**禁止留空**。
2. 非功能需求**必须有关联的验证方式**（测试/演练/桌面推演/明确标注未测）。
3. 团队/行业已有**非功能基线清单**（如企业下发的 N 大项 M 细项）时，作为 `standards/enterprise/quality/`
   导入并在 Phase 0 对照本清单逐项检视——**框架给维度，企业给细项**。

## 2. 非功能需求在四阶段的落地（强制：不许只写在需求里）

| 阶段 | 动作 | 交付物 |
|---|---|---|
| **需求** | 从基线清单识别本项目**尚未满足**的非功能需求，纳入范围 | 技术方案建议 / BRD 非功能章节 |
| **分析 · 设计 · 开发** | 针对未满足项制定改造方案；设计文档必须有**非功能设计章节** | 设计说明书 + 评审记录 |
| **测试** | 对照改造内容评估非功能测试必要性，识别测试域与策略，执行 | 非功能测试场景 + 测试报告 |
| **部署 · 切换** | 投产/切换前做**非功能验收检查**；演练问题与风险成单 | 演练报告 + 风险清单 |

**强制条款**：

1. 设计文档**必须**含非功能设计章节；缺失则 Gate 2 不通过。
2. **测试版本下发前完成非功能测试必要性评估**——未评估不得下发（可作 Gate 3/4 检查项）。
3. 投产前必须提交"演练问题 + 投产风险"清单，不能只报"演练通过"。

## 3. 非功能测试识别表

开工前填一张识别表，把"要不要测"变成可核对的清单：

| 分类 | 内容 | 数量示例 |
|---|---|---|
| 性能测试 | 业务指标输入（TPS/响应时间/并发） | 按项目 |
| 非功能测试 | 容灾/熔断/限流/降级/恢复类验证 | 按项目 |
| 功能测试相关 | 需从功能视角确认的验证项 | 按项目 |
| 环境/部署配置 | 双机房/单元化/网络配置确认 | 按项目 |
| 技术栈选型与分析设计 | 架构能力确认项 | 按项目 |
| **不涉及测试** | 明确判定不需要测的项（**必须写明理由**） | 按项目 |

**强制条款**：每一行都必须给出"测 / 不测 + 理由"；"不涉及测"**必须**写理由，禁止空白。

## 4. 架构分层 × 故障类型映射（故障注入的核心工具）

把架构按技术层级分层，每层对应一组可注入的故障类型——**这样故障用例不会漏，也不会乱**。

| 层 | 含什么 | 可注入故障类 |
|---|---|---|
| **① 基础设施层** | 平台、服务器、存储、网络、外设 | 裸金属、存储、外设、网络、服务器、机柜、微模块、机房、城市（异地） |
| **② 基础平台层** | 容器平台、操作系统、数据库、队列、缓存 | 容器、操作系统、数据库、队列、缓存 |
| **③ 开发运维层** | 开发组件、运维组件、DevOps 平台 | 代码、进程、微服务框架、容器、缓存、队列、数据库、操作系统、裸金属 |
| **④ 应用平台层** | 技术组件（③ 之外） | 代码、进程、微服务框架、容器、缓存、队列、数据库 |
| **⑤ 应用组件层** | 业务应用组件 | 代码、进程、微服务框架、容器、缓存、队列、数据库 |

**常见故障动作**（取自各故障类）：

进程重启 / 进程挂起 / 进程宕机 / CPU 高 / 内存抢占 / 磁盘容量满 / 网络包损坏 / 网络时延 /
FullGC 时间长 / 优雅下线（普通微服务、网关）/ 主从切换 / 熔断（组件内、组件间、单元间）/
限流 / 降级 / 连接池打满 / 心跳保活 / 自动重连 / 单元化弹性弹出与回弹 / 容灾切换。

**强制条款**：

1. 非功能测试**必须**按"业务需求 → 架构层 → 故障类型 → 具体故障动作"的链路推导，
   **禁止凭感觉挑几个故障来测**。
2. 每层至少覆盖**一个必选故障**（见 §5）。

**示例**：业务需求要求"熔断机制" → 该组件属**应用组件层** → 按映射筛选"熔断-组件内/组件间"故障 → 定用例。

## 5. 故障案例选择（等价类 + 必选/可选）

| 策略 | 说明 |
|---|---|
| **等价类划分** | 同一架构层、同一技术类型下，**技术架构相同的微服务表现一致**——每个故障类选 1 个代表即可，不必全测 |
| **必选故障** | 每个故障类选 1 个代表故障作为**必选**；结合历史生产事件形成的故障也列为必选 |
| **可选故障** | 各系统按自身技术架构与运维实际，从剩余故障中筛选 |
| **交易选取** | ① 覆盖生产流量最大的交易 ② 覆盖业务重要度高的交易 |
| **组件/微服务选取** | ① 覆盖所有单元类型（若有）② 覆盖所有使用的中间件 |

**强制条款**：

1. 必选故障**不得因排期紧张而删减**；确实无法测的**必须**写明"未测 + 原因 + 风险"。
2. 场景分**动态测试验证**（真跑，联机/批量）与**静态桌面推演**（跑不了就推演并记录推演过程）两类；
   推演场景**必须在报告里与实测场景分开列**。

## 6. 性能：瓶颈模型与调优七步法

### 6.1 瓶颈模型

**性能瓶颈** = 某环节因资源限制、设计缺陷或负载过高，导致整体性能受限（成为短板）。

| 诱发因素 | 四类连锁反应 |
|---|---|
| 资源限制 | 响应时间变长 |
| 设计缺陷 | 吞吐量下降 |
| 负载过高 | 成功率下降 |
| | 资源占用异常 |

**强制条款**：性能问题定位**必须**落到"哪个环节 + 哪个诱发因素"，禁止结论停在"系统慢"。

### 6.2 性能调优七步法（按序，不许跳）

1. **压力场景分析**：压力线程数、TPS、响应时间、错误率——先量化现状。
2. **系统架构分析**：代码逻辑、请求路径、组件列表——画出链路。
3. **响应时间分析**：分段（网络/应用/DB/下游）、分层。
4. **全局监控分析**：建立性能分析决策树。
5. **定向监控分析**：沿瓶颈验证链路定向采集。
6. **判断性能瓶颈**：明确**具体瓶颈点**（不是"整体偏慢"）。
7. **提出解决方案**：执行方案并**比对结果**（改前 vs 改后同口径数据）。

**常用工具**：APM、火焰图、Arthas、系统命令（top/iostat/netstat）、JMeter。
**强制条款**：第 7 步的"比对结果"必须落盘（改前后两组数据），否则不算调优完成。

## 7. 混沌工程（故障注入）

**手段**：故障注入 + 交易发起（联机/批量）+ 运行监控 → 运行评价。

**目的**：以低风险、低成本方式"提前见识"故障，检验系统在各种错误下的反应，
建立系统承受生产压力的信心。

**强制条款**：

1. 故障注入**必须有爆炸半径控制**（影响范围、持续时间、回退开关）与**观测手段**，禁止裸测。
2. 注入前**必须**确认回退路径可用（见 change-management.md §4）。
3. 生产环境注入按 **M 级变更**管理（重大变更，需用户明确批准）；测试环境按 N 级。
