# 配置管理规范（Configuration Management）

> 版本: 1.0.0 | 状态: active | 适用范围: 全部阶段
> 定义：**识别配置项 → 基线化 → 控制变更 → 记录状态**。回答"哪一版是经过验证、可作为交付依据的"。
> 本规范是"体系化"的地基：没有基线，Gate 通过与否就无法复现。

---

## 0. 与 `CMP-配置管理.md` 的区别（重要，别混）

| 名称 | 是什么 | 范围 |
|---|---|---|
| `CMP-配置管理.md`（见 process.md §4.2） | **环境变量/配置项的单一真源清单**，与 `.env.example` 对齐 | 一个文件 |
| **本规范（SCM）** | **配置管理过程**：识别配置项、定义基线、控制变更、状态报告 | 一套过程 |

两者同名不同义。本项目里 `CMP-*.md` 是 SCM 管理的**一个配置项**，不是 SCM 本身。

## 1. 配置项（Configuration Item）

**配置项** = 为接受配置管理而得到标识的工作产品。

必须纳入管理的配置项类型：

| 类别 | 例子 | 标识方式 |
|---|---|---|
| 文档 | 需求/设计/测试/运维文档 | `<项目代码>_<文档类型码>_<版本号>`（见 §4） |
| 源代码 | 源文件、脚本、构建配置 | Git 提交哈希 + 标签 |
| 执行码/制品 | 构建产物、安装包 | 制品名 + 版本号 + 校验和 |
| 环境配置 | `.env` 模板、部署清单 | 与 `CMP-配置管理.md` 对齐 |
| 迁移脚本 | DDL / 数据迁移 | 有序编号 + 幂等标记 |

**强制条款**：

1. 配置项**必须可唯一标识**（文件名含版本号，或由 Git 标签/提交哈希标识）。
2. 配置项**必须可追溯到产出它的活动**（哪个 Gate、哪次评审通过）。
3. **禁止**把未标识版本的文件当作交付依据（如 `final_v2_真正最终.docx`）。

## 2. 基线（Baseline）

**基线** = 一个或多个配置项的集合，在阶段结束点经**验证与确认**后获得认可，为后续变更提供稳定基础。

### 2.1 基线的形成标志（强制）

基线**不是"写完了"，而是"评审通过了"**。形式：

| 基线 | 形成标志 | 对应框架 Gate | 主要配置项 |
|---|---|---|---|
| **B1 需求基线** | 需求评审通过（BRD 验收标准用户确认 + 追踪矩阵闭环） | **Gate 0** | BRD / GAP / request.md |
| **B2 分析基线** | 分析走查闭环（PFA/SRS/DAS + WTR 无未决项） | **Gate 1** | PFA / SRS / DAS / WTR |
| **B3 设计基线** | 设计评审通过（ODD/架构 + ADR + CLM/PMD 基线化） | **Gate 2** | ODD / SAD / SAS / ADR / CLM / PMD |
| **B4 开发完成基线** | 单元 + 组件（集成）测试准出 | **Gate 3** | 代码 + 测试证据 + 构建产物 |
| **B5 产品基线** | 功能测试准出（+ 非功能清单过项） | **Gate 4** | 发布制品 + FTR/NFTR + 手册 |
| **B6 交付基线** | 部署演练/切换验证通过 | **Gate 5** | RUNBOOK + 部署制品 + DRR |

> 裁剪：小型项目可合并 B2/B3（分析设计一体）与 B4/B5，但**每个实际发布的版本必须至少有一个基线**，
> 且必须在进度真源登记"基线名 + 形成日期 + 依据".

### 2.2 基线纪律（强制）

1. **基线一旦形成，修改必须走变更流程**（见 change-management.md），禁止就地覆盖。
2. 基线变更 → **版本号递增**（`_01` → `_02`），旧版保留可追溯（Git 标签或归档目录）。
3. 每个基线**必须可复现**：给出提交哈希/制品校验和 + 复现命令。
4. 进度真源必须含**基线登记表**（基线名 / 日期 / 依据 / 标识）。

### 2.3 基线登记表（模板）

| 基线名 | 标识 | 形成日期 | 形成标志（评审记录链接） | 备注 |
|---|---|---|---|---|
| B1 需求基线 | `<项目>_U_01` | | | |
| B5 产品基线 | `<项目>_V1.0_01` | | | |

## 3. 配置库（三库模型 → 小团队降档）

企业做法是物理三库，个人/小团队用 **Git 分支 + 标签**等价实现：

| 企业概念 | 用途 | 本框架等价实现 |
|---|---|---|
| 开发库 | 日常开发，频繁变动 | 特性分支 / `main` 的工作区 |
| 受控库（配置库） | 存放已基线化配置项 | **Git 标签**（`v1.0.0`）+ 受保护分支 |
| 产品库 | 已发布/已交付版本 | Release / 制品库 / 归档目录 |

**强制条款**：

1. 基线化 = **打标签**（`git tag -a <基线标识> -m "<形成标志>"`），禁止只靠分支名承载。
2. 交付物**必须**从产品库取，禁止从开发工作区直接交付。
3. 发布制品**必须**记录校验和（`sha256`），交付说明里写出。

## 4. 文档编号规范（配置项标识）

编号格式：

```
<项目代码>_<文档类型码>[_<文档描述码>]_<版本号>
```

- **文档类型码**：2–3 位字母，标识文档类型（下表）。
- **文档描述码**（可选）：区分同类型的不同文档。
- **版本号**：按顺序数字编号；由工具管理的可用系统序号。

| 类型码 | 文档 | 类型码 | 文档 |
|---|---|---|---|
| `U` | 用户需求 | `HD` | 总体设计说明书 |
| `PFD` | 项目应用分析说明书 | `CD` | 细化设计说明书 |
| `IG` | 安装手册（增量） | `MG` | 维护手册 |
| `UM` | 用户手册 | `VD` | 版本说明书 |

示例：总体设计文档编号 `BBB_HD[_QD_]_01`。

**强制条款**：正式交付文档的文件名**必须**含 `<类型码>_<版本号>`；版本号与 Git 标签一致；
命名规则写入 `docs/glossary.md` 或项目 README，避免各人自造。

## 5. 配置管理活动（策划 → 实施 → 审计 → 状态报告）

| 活动 | 做什么 | 产出 |
|---|---|---|
| **策划** | 定配置项范围、基线计划、命名与编号规则、分支/标签策略 | 配置管理计划（可并入项目计划；小项目写在 README） |
| **实施** | 标识配置项、定义基线、库控制、变更控制、出入库 | 基线登记表 + Git 标签 |
| **审计（配置审计）** | 检查交付物与基线一致；检查文件齐全与命名合规 | 审计记录（并入 Gate Review 检查项） |
| **状态报告** | 报告变更进展与基线状态 | 进度真源中的基线段 |

**配置审计的两类**：

- **功能配置审计（FCA）**：配置项**功能**与需求一致（对照 BRD 验收标准）。
- **物理配置审计（PCA）**：配置项**清单/命名/版本**与规范一致（对照本规范 §1/§4）。

**强制条款**：Gate 5 交付前必须做一次 PCA；FCA 由测试证据（FTR）承担，不重复做。
