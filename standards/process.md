# 工艺流程管理规范（Process Engineering）

> 版本: 2.3.0 | 状态: active | 适用范围: 全部开发阶段
> 定义：**七阶段工艺闭环 + 产出物依赖链 + 强制沉淀点**。本版对齐企业级「工程活动工艺全流程」
> 模型（需求→分析→设计→开发→测试→部署→维护），为个人/中小项目提供**可缩放的轻量产物**，
> 保证每类活动都有可追溯的落盘交付物（工艺流程沉淀），禁止"只做不沉淀"。

---

## 1. 工艺全流程总览（七阶段闭环）

```
Gate 0       Gate 1      Gate 2      Gate 3     Gate 4      Gate 5
需求通过     分析通过     设计通过     实现通过    测试通过     交付通过
  │            │           │           │          │           │
  ▼            ▼           ▼           ▼          ▼           ▼
[需求] ───► [分析] ───► [设计] ───► [开发] ───► [测试] ───► [部署] ───► [维护]
 (澄清拆解映射) (方案转化)  (选型+框架+数据) (编码)    (验证)     (上线)      (运维)
                                                                         │
                                                              ┌──────────┘
                                                              ▼
                                                        [复盘/经验回流]
```

| 阶段 | 核心目标 | 子活动流 | 关键交付物（沉淀点） |
|---|---|---|---|
| 需求 Requirement | 把一句话/方向转化为可验收的业务需求 | 战略解析 → 需求澄清 → 需求拆解 → 需求映射 | request.md · BRD（目标态）· GAP（差距）· TSP（技术方案建议）· FPE/WLE（估算）· RVW（评审） |
| 分析 Analysis | 把需求转化为可实现的技术方案 | 应用分析 → 架构分析 → 实施分析 → 测试方案设计 | PFA（功能分析）· SRS（需求规约）· DAS（数据分析）· FTP（测试方案）· WTR（走查记录） |
| 设计 Design | 把方案转化为可编码的设计 | 技术框架选型 → 框架设计 → 数据库与数据设计 → 性能风险登记 | ODD（总体设计）· SAD/SAS（架构文档）· ADR · CLM（概念逻辑模型）· PMD（物理模型/DDL）· ETL · PRT（性能风险） |
| 开发 Development | 把设计转化为可测试的代码 | 编码准备 → 编写代码 → 提交验证 → 代码复查 | CODE（代码）· WTR（走查）· 进度日志 |
| 测试 Test | 验证代码满足需求与非需求 | 单元 → 组件 → 集成 → 业务功能 → 非功能 | FTR（功能测试报告）· NFTR（非功能测试报告）· 测试证据 |
| 部署 Deployment | 把测试通过的产物部署到目标环境 | 环境准备 → 应用部署 → 投产演练 → 切换验证 | HRP（资源建议）· TTM（部署文档）· DRR（演练/切换报告） |
| 维护 Maintenance | 让系统可持续运行与交接 | 运维手册 → 日常维护 → 变更管理 → 复盘沉淀 | RUNBOOK（维护指南）· CHP（变更记录）· CMP（配置管理）· PSR（项目总结） |

> 管理类文档（项目章程 PCH / 项目计划 PP / 配置管理 CMP / 质量保证 QAP / 风险管理 RMP /
> 变更管理 CHP / 沟通管理 CMP2 / 项目总结 PSR）**贯穿始终**，不单独占一个阶段。

### 关口（Gate）定义

| 关口 | 通过条件 | 产出物 |
------|---------|--------|
| **Gate 0 前置** | **工程基线已立并落盘**（§1.5：运行环境/语言框架版本/实现标准/依赖选型） | 基线文档或 README 技术基线节 |
| Gate 0 需求通过 | 澄清完成（grill-me 或假设表）、BRD/GAP 目标与差距分离、验收标准用户确认 | request.md + BRD + GAP |
| Gate 1 分析通过 | PFA/SRS/DAS 走查闭环；技术路线与部署方向明确 | PFA + SRS + DAS + WTR |
| Gate 2 设计通过 | 技术框架选型有 ADR；模块契约明确；数据模型（CLM/PMD）基线化 | ODD/SAD/SAS + ADR + CLM/PMD |
| Gate 3 实现通过 | 每批测试绿 + 文档同步 | 代码 + 进度日志 + 提交 |
| Gate 4 测试通过 | FTR 全部用例有证据；非功能清单过项 | FTR + NFTR |
| Gate 5 交付通过 | quality-gate 全绿 + 已知限制清单 | RUNBOOK + 交付总结 + 复盘 |

关口规则：

1. **关口不可跳过**（`--minimal` 模式也只压缩范围——小任务可合并交付物文件，但**沉淀点内容不得消失**）。
2. 关口结论写入进度真源（含"通过/返工"与理由）。
3. 返工闭环：Gate 失败 → 问题记录 → 修复 → 重新验证 → 关口通过。

### 1.5 项目开工基线（Gate 0 前置：先立基线，再谈需求）★

> 开工前**必须**书面约定工程基线并落盘。基线是"环境一致"与"生产级"的前提；
> **基线未确立不得进入 Gate 0**——禁止边做边定技术栈（技术栈漂移是返工与重写的常见根因）。

必须约定的四类（缺任一类视为未开工）：

| 类别 | 约定什么 | 例 |
|---|---|---|
| **运行环境** | 开发/测试/生产环境形态与目标平台 | 本机开发 + Linux 部署；容器或裸机 |
| **语言与框架** | 主语言、框架、**版本号**（精确到可复现） | Python 3.12 + FastAPI；Node 22 + Vue 3 |
| **实现标准** | 生产级或演示级；性能与安全底线 | **默认生产级**；确为演示级须显式标注交付边界 |
| **依赖选型** | 数据库/消息队列/缓存的默认选择 | 关系库 MySQL/PostgreSQL/SQLite/Elasticsearch；消息队列优先 Pulsar；缓存优先 Redis |

落盘位置（二选一，全项目统一）：项目 `README.md` 的"技术基线"节，或 `docs/engineering-baseline.md`
（属**现状快照**类，随架构变更重写——见 documentation.md §3「事实三分」）。

**强制条款**：

1. **未落基线不得开工**——作为 Gate 0 的前置检查项逐条核对。
2. **默认生产级**：除用户明确指定演示/demo 外一律按生产级实现（错误处理、配置外置、可观测性、
   数据一致性均按生产要求）；禁止把"先做演示再补"当默认路径。
3. **默认选型可偏离，但必须写理由**：偏离"消息队列优先 Pulsar、缓存优先 Redis"这类默认时，
   在 ADR 或基线文档写明取舍（成本/生态/团队熟悉度/部署约束）。
4. **版本必须锁定**：lockfile 入库，浮动版本禁止进生产（与 configuration-management.md 一致）。
5. **基线变更受控**：改运行环境/语言版本等基线项，先按 §6 需求变更联动评估波及面，
   再按 change-management.md 定级（涉及运行环境按 M 级）。

## 2. 需求阶段：三件事 + 一道评审（强制：澄清 → 拆解 → 映射 → 评审）

> 一句话需求**必须**走完这三件事再进入设计。禁止"直接写代码"式开局
> （`--minimal` 下可合并产物文件，但三步内容都要落到 `docs/`）。

### 2.0 需求进入：形态判定 → 战略解析 → 三个层次

#### 2.0.1 需求形态判定（先判从哪来）

不是所有"需求"都走同一条路。先判形态，再选入口：

| 形态 | 例子 | 入口 |
|---|---|---|
| **战略话语** | "我们要做 AI 客服" / "把账号体系统一" | **先走 §2.0.2 战略解析** |
| **功能请求** | "详情页加导出按钮" | 直接进 §2.1 澄清 |
| **缺陷/异常** | "登录偶尔 500" | 先诊断根因，根因是需求缺口才转回本节 |
| **存量改造** | "重构订单模块" / "把支付从 go 迁到 java" | **走 §10 特殊项目形态** |

#### 2.0.2 战略解析（Strategic Analysis）

**干什么**：把方向性诉求/战略意图收敛成**可澄清的业务需求**——回答"我们到底要做什么、给谁做、凭什么值得做"。
不产出代码，产出一页决策依据（可并入 request.md，亦可独立 `STR-<主题>.md`）。

| 解析项 | 回答的问题 |
|---|---|
| 问题定义 | 现状痛点/机会是什么？（与 GAP 衔接） |
| 受益者 | 谁受益？怎么受益？（角色 + 场景） |
| 可度量目标 | 成功后怎么证明？（指标，如"客服转人工率降 50%"） |
| 约束与假设 | 时间/资源/合规/技术限制？哪些假设待验证？ |
| 取舍 | 明确不做/推迟什么（范围裁剪，避免什么都想要） |

**强制条款**：

1. 战略话语**必须**先走战略解析再进澄清；跳过战略解析 = 把方向性诉求直接当业务需求，返工主因。
2. 战略解析**必须产出可度量目标**——写不出指标的方向说明还没想清，继续收敛，禁止带病前行。
3. 目标后续变化 → 走 §6 需求变更联动。

#### 2.0.3 需求的三个层次（先对齐层次，再谈内容）

需求不是一坨，是**逐层收敛**的三层；混层讨论是需求返工的主因。

| 层次 | 是什么 | 产出 | 谁看得懂 |
|---|---|---|---|
| **意向需求** | 方向性诉求，尚未结构化 | 一句话 / 访谈原始记录 | 提出方 |
| **业务需求** | 用户**视角**：用软件完成什么任务、怎么完成 | **业务需求说明书**（场景化，不涉实现） | 业务方 + 开发方 |
| **需求规格** | 开发**视角**：准确到可据以开发 | 项目应用分析说明书 / SRS | 开发方 + 测试方 |

**强制条款**：

1. 澄清阶段**必须**标注当前讨论处于哪一层；**禁止**用意向层的话直接进设计。
2. 业务需求与需求规格**必须分开成文**（可合并文件，但层次不能混）；
   业务需求写"用户要完成什么"，需求规格写"系统据此做什么"。
3. 层级未收敛（业务需求未定）时**不得**进入设计阶段。

### 2.1 需求澄清（Clarification）

把用户原话/方向逼成共享理解，防零澄清返工：

1. 用 **grill-me** 技能拷问（用户明确免问时改走假设表）：
   - 域模型关键词（产品 vs 运行时 vs 框架）、部署拓扑（同机/多机/内网/代理）、
     可用性依赖方向、配置是否需要 UI 可改、默认行为（"全部"为默认）；
   - 对外输出类需求必须澄清：用途受众 / 形态规模 / 内容真源 / 验收标准。
2. 产出 `docs/00-request/request.md`：**用户原话**（完整抄录）+ 提炼 + 假设表
   （每条假设含依据与影响）+ 目标项目路径锚定（防目标漂移）。
3. 澄清结论逐条记录，含"用户确认了哪句话"（可追溯）。

### 2.2 需求拆解（Decomposition）

把澄清后的需求拆成"目标态"与"差距"两部分（**禁止混淆**，见 §5）：

- **BRD（业务需求说明书，目标态）**：回答"目标系统做什么"——背景与目标、名词与概念、
  用户角色与场景、功能模块清单（P0/P1/P2 分级）、每条功能的可测试**验收标准**（用户确认）。
  命名：`BRD-<主题>.md`。
- **GAP（差距分析报告，快照）**：回答"当前系统有什么问题"——现状快照、问题清单、
  现状→目标 delta、改进项映射。命名：`GAP-<主题>.md`。全新项目无现状可省略，但要写明"无现状"。
- **估算（可选，按规模）**：功能点估算（FPE）、工作量估算（WLE）——项目计划依据。

### 2.3 需求映射（Mapping）

把 BRD 需求映射到实现要素，保证"需求→实现→验证"三向可追溯：

| 映射方向 | 落到哪 | 说明 |
|---|---|---|
| 需求 → 功能模块 | 设计阶段 ODD/架构文档 | 每条需求标注所属模块 |
| 需求 → 数据实体 | 设计阶段 CLM/PMD | 每条需求标注涉及的数据实体 |
| 需求 → 接口/API | 分析阶段 SRS、设计阶段接口文档 | 每条需求标注对外接口 |
| 需求 → 验收标准 | FTR 需求测试追溯矩阵 | 每条验收标准有测试用例编号 |

- 中型以上项目建 **需求追踪矩阵**（`docs/01-requirements/traceability.md`）：
  `需求ID → 功能模块 → 数据实体 → 接口 → 测试用例ID → 状态`。
- 任何需求变更先更新矩阵再动代码（见 §6 变更联动）。

**追溯必须是双向的**（只做单向 = 半个追溯）：

| 方向 | 含义 | 能回答的问题 |
|---|---|---|
| **纵向（本产品内）** | 需求 ↔ 设计 ↔ 代码 ↔ 测试 ↔ 交付物 | "这条需求实现了没有？有没有代码没需求？" |
| **横向（产品/模块之间）** | 需求 ↔ 上下游产品与接口 | "这个改动影响谁？谁在依赖我？" |

**强制条款**：

1. 纵向追溯**必须**闭环：每条需求能指到测试用例，每个测试用例能指回需求（**孤儿需求与孤儿用例都要清零**）。
2. 横向追溯**必须**在需求影响跨模块/跨系统时建：标出上游依赖与下游消费方（配合 `interfaces.md`）。

### 2.4 需求评审（七性检查）

需求进入设计前的最后一道关。逐条自检，**任一条不达标则 Gate 0 不通过**：

| # | 检查项 | 问什么 |
|---|---|---|
| 1 | **完整性** | 该有的都有了吗？边界、异常、非功能需求覆盖了吗？ |
| 2 | **规范性** | 格式、命名、术语符合 `documentation.md` 与术语表吗？ |
| 3 | **准确性** | 描述无歧义吗？两个人读会得出同一结论吗？ |
| 4 | **一致性** | 需求之间不矛盾吗？与已有系统约束不冲突吗？ |
| 5 | **整合性** | 与现有架构、数据、接口能拼上吗？会不会破坏既有契约？ |
| 6 | **成熟性** | 需求稳定到可以开发了吗？还是还在反复变？ |
| 7 | **可实施性** | 技术上做得到吗？资源/时间/依赖允许吗？ |

**强制条款**：评审结论**必须**落盘（`docs/01-requirements/` 评审记录或在 BRD 内标注），
逐条写"通过 / 不通过 + 理由"；**禁止只写"评审通过"四个字**。

## 3. 设计阶段四件事（强制：选型 → 框架设计 → 数据库设计 → 维护准备）

> 涉及技术栈/架构/数据的项目，**必须**沉淀这四类设计，禁止"选型只存在对话里"。

### 3.1 技术框架选型（Framework Selection）

1. 产出 `docs/02-design/tech-selection.md` 或直接 ADR：候选方案 ≥ 2 个，
   对比维度（能力覆盖/维护成本/性能/生态/团队熟悉度/部署约束），给出**推荐 + 理由**。
2. 显著决策写 **ADR**（`docs/02-design/decisions/adr-<nnn>-<slug>.md`）：
   背景 / 候选 / 决策 / 后果。选型即决策，必须落盘。
3. 采用"最小可行栈"：每加一个中间件/框架必须有理由，复杂度要 ADR 背书。

### 3.2 框架设计（Framework/Architecture Design）

1. **ODD（总体设计说明书，轻量 = `architecture.md`）**：总体目标、设计原则、模块划分、
   进程/部署拓扑、模块间契约。命名 `ODD-<主题>.md` 或 `architecture.md`。
2. **SAD/SAS（架构文档，按规模）**：需要时按专题拆分——`SAD-<专题>.md`（软件架构文档，
   模块级设计）/ `SAS-<专题>.md`（系统架构设计说明书，系统级拓扑/组件交互）。
3. 模块拆分过四维检验（上下文纯净度/时间尺度/风险边界/生命周期，见 §7），
   拆分或合并必须有 ADR 或架构文档论证，禁止"凭感觉拆"。

### 3.3 数据库与数据设计（Data/Database Design）★

> 凡涉及持久化（数据库/缓存/文件/消息），必须沉淀三级模型，禁止"建表凭感觉"。

| 层级 | 产物 | 内容 | 命名 |
|---|---|---|---|
| 概念模型 | CLM | 实体、关系、业务规则（ER/关系图，不涉具体库） | `CLM-<域>.md` |
| 逻辑模型 | CLM 续 | 字段、类型、主外键、约束（逻辑层） | `CLM-<域>.md` |
| 物理模型 | PMD | 具体 DDL、表结构、索引策略、分区、迁移脚本 | `PMD-<域>.md` + `migrations/` |
| 数据流转 | ETL/DAS | 数据源、抽取/转换/加载链路、存量数据迁移方案 | `ETL-<主题>.md` |

- 表结构变更必须配**迁移脚本**（版本化、可回滚），禁止只改代码不改库脚本。
- 数据敏感字段（密码/密钥/个人信息）加密或脱敏策略必须写入 PMD。

### 3.4 性能与风险登记（PRT）

- `PRT-性能风险跟踪表.md`：已知性能风险、量化指标（有基准才写数字）、应对方案、状态。
- 无基准不写数字（见 performance.md）。

### 3.5 架构管控与开源引入 ★

> §3.1 定"选什么"，§3.2 定"怎么分"，本节定"**守不守规矩**"。
> 设计能不能通过 Gate 2，取决于本节两条：落标检查 + 引入评估。

#### 3.5.1 架构原则与落标检查

**先立原则，再守原则**：项目启动时定少量（3–7 条）架构原则，写进 `architecture.md`；
此后每次设计评审做一次**落标检查**——设计是否违反已定原则。

**落标检查表**（Gate 2 逐条勾选，结论落盘）：

- [ ] 是否**违反已定架构原则**？（逐条对照，违者须 ADR 说明为何破例）
- [ ] 是否**引入未经评估的新技术组件/依赖**？（→ 走 §3.5.2）
- [ ] 模块边界是否清晰（过 §7 四维检验）？
- [ ] 是否**与现有系统契约兼容**？（配合 `interfaces.md` 评估消费方）
- [ ] 是否**可回退**？（不可逆的架构决策须显式标注并取得批准）

**强制条款**：破例**必须**有 ADR；**禁止**"先用着，回头补文档"。

#### 3.5.2 开源引入评估（引入任何第三方依赖前）

| 维度 | 要查什么 |
|---|---|
| **许可证** | 是否允许本项目使用方式？有无 copyleft 传染风险？商用/分发是否受限？ |
| **维护活跃度** | 最近发布、issue 响应、维护者是否仍在？ |
| **安全性** | 已知 CVE、供应链风险（依赖树深度、维护者可信度） |
| **能力匹配** | 真的需要它吗？能否用已有组件或几十行代码替代？ |
| **退出成本** | 将来要换掉有多难？有没有抽象层隔离？ |

**强制条款**：

1. 引入开源/第三方组件**必须**完成上表评估并落盘（可并入 ADR 或 `tech-selection.md`）。
2. 许可证**必须**记录（写入 `tech-selection.md` 或 `docs/02-design/` 下的依赖清单），
   **禁止**引入许可证不明或与本项目发布方式冲突的组件。
3. 依赖**必须**锁版本（lockfile 入库），**禁止**浮动版本进生产。

#### 3.5.3 系统演进路线（多期项目）

涉及多期建设时，设计阶段须给出：

```
现状对标（现有系统 ↔ 业务价值流/职责）
   → 目标规划（要整合谁、新增谁、下线谁）
   → 演进路线（分期，每期的基线与交付物）
```

**强制条款**：分期路线**必须**写清**每期结束时形成哪个基线**（对齐 configuration-management.md §2.1）。

## 4. 维护指南（Maintenance Guide）

> 交付前**必须**给"接手的人/未来的自己"可运维的文档，禁止"代码能跑就行"。

### 4.1 运行手册（RUNBOOK）

`docs/07-ops/runbook.md`（或 `RUNBOOK.md`）必含：

| 章节 | 内容 |
|---|---|
| 部署 | 环境要求、构建/启动/停止命令、配置项清单（.env.example 对照） |
| 排障 | 常见故障症状 → 排查命令 → 处理步骤（含日志位置、健康检查） |
| 回滚 | 版本回退步骤、数据回滚方案（迁移脚本 down） |
| 日常维护 | 备份策略、日志清理、监控项、定期任务 |

### 4.2 运维记录与变更管理

- `docs/07-ops/CHANGELOG.md` 或 `CHP-变更记录.md`：每次部署/配置变更记时间、内容、影响、回退。
  **表结构与分级规则见 `change-management.md` §7**（级别 R/N/M/E + 回退条件 + 实际结果）。
- `CMP-配置管理.md`：环境变量/配置的单一真源清单（与 `.env.example` 对齐）。
- **配置项与基线**：哪些产物受管、基线何时形成、怎么打标签 → 见 `configuration-management.md`。
- 部署产物：环境资源建议（HRP，按规模）、部署文档（TTM）、演练/切换报告（DRR/CTR，按规模）。

### 4.3 环境管理（环境基线）

**环境三分类 + 命名规范**：

| 环境 | 用途 | 数据要求 |
|---|---|---|
| **开发环境** | 日常开发调试 | 本地/虚拟数据 |
| **测试环境** | 验证、演练、非功能测试 | **脱敏数据**（禁止直连生产数据） |
| **生产环境** | 对外服务 | 真实数据 |

命名规范：`<系统名>-<环境类型>-<序号>`（如 `订单-测试-01`）；**禁止随意起名**。
按需增加预发/演练环境时同样遵守命名，并在环境清单登记。

**强制条款**：

1. **环境清单单一真源**：环境清单（环境名/地址/用途/数据等级）写在 RUNBOOK 一处；
   环境增删改走配置管理登记（configuration-management.md），**禁止环境信息散落各处**。
2. **生产环境准入**：生产环境的任何变更走 `change-management.md`（分级 + 回退预案）；
   **禁止"直接上去改一下"**。测试环境变更按 N 级，生产按 M 级。
3. **环境一致性**：环境差异**只用配置键表达**（禁 OS/主机名/路径探测分支）；
   配置漂移用 `CMP-配置管理.md` 与 `.env.example` 对照检测。
4. **数据隔离**：测试/演练环境禁止直连生产数据；确需使用 → 脱敏 + 登记使用范围。

## 5. 目标 vs 差距 分离原则

需求阶段交付物分两类，**严禁混淆**：

| 文档类型 | 定位 | 回答 | 时间属性 |
|---------|------|------|---------|
| **BRD**（目标态） | 业务需求 | 目标系统做什么？ | 长效（版本化） |
| **GAP**（差距分析） | 现状→目标 delta | 当前系统有什么问题？ | 快照（时间点） |

判定准则：

| 段落性质 | 归属 |
|---------|------|
| "系统应该做什么" | BRD |
| "当前系统有什么问题/痛点/短板" | GAP |
| 1-2 句简短业务背景（服务于目标定义） | BRD 可保留 |
| 独立的「现状诊断」「问题清单」「痛点表」段落 | 必须拆到 GAP |

设计/分析阶段的文档同样遵循：目标导向文档（ODD/SAD/SAS/CLM/PMD）只描述 target state；
现状问题用单行引用：`> 现状与差距见 [[...GAP-<主题>|GAP-<主题>]]`，禁止内嵌。

## 6. 需求变更联动流程

> 本节管**需求侧联动**（改了需求要顺流改哪些文档）；变更本身的**分级/授权/回退/后评价**
> 见 `change-management.md`。两者组合使用：先按本节评估波及面，再按变更规范定级与授权。

需求变更（用户一句话、评审意见、实现中发现矛盾）必须走：

1. **记录变更**：更新 `docs/00-request/request.md`（变更原因 + 新旧对比）+ 需求追踪矩阵。
2. **评估波及**：按 documentation.md 依赖矩阵评估：BRD 验收标准 / 架构 / 数据模型 / 计划 / 测试 / 运行手册。
3. **决策记录**：变更显著时补 ADR（如范围扩大引入新组件、表结构变更）。
4. **顺流更新**：变更只能顺流传播，禁止只改代码不更新文档。
5. **验证**：受影响的验收标准重新跑测试，证据落 `docs/05-testing/`。

## 7. 模块/组件拆分四维检验

拆分模块、Agent、服务前，用四维检验防止过度拆分：

| 维度 | 检验问题 | 冲突信号（不应拆/拆了要说明） |
------|---------|------------------------------|
| **上下文纯净度** | 拆分后各自的上下文是否加载互斥知识？ | 强耦合领域逻辑被拆散 |
| **时间尺度** | 两者的运行/会话模式是否一致？ | 高频短任务与长会话任务合并 |
| **风险边界** | 权限/影响范围是否兼容？ | 只读建议与写操作混在一个角色 |
| **生命周期** | 演进速度/发布节奏是否一致？ | 频繁变更与冻结稳定模块同仓 |

任何拆分/合并都必须有 ADR 或架构文档论证，禁止"凭感觉拆"。

## 8. 能力组织判定（Agent vs 工具 vs 服务）

新增能力时先判定形态，避免"什么都用 Agent / 什么都写成工具"：

```
能力需要 LLM 推理或多轮决策？
  ├── 是 → Agent（独立角色：system prompt + 工具集 + 记忆 + 心跳）
  ├── 否 → 是确定性查询、被多方复用？
  │         ├── 是 → 工具/接口（函数、CLI、REST、MCP server）
  │         └── 否 → 普通业务函数/服务
  └── 需要长期积累上下文？→ 加记忆/会话管理
```

判定原则：

1. **能确定性实现就不用 LLM**（成本、延迟、可测试性）。
2. **能被多方复用就拆成工具/接口**（避免复制逻辑）。
3. **需要完整人格/上下文积累才建 Agent**（独立角色）。

## 10. 特殊项目形态（重构 / 迁移）

> 默认七阶段工艺的入口是"新项目/新功能"；本节定义两种**存量改造**形态的专门入口。
> 核心差别：存量系统已有"现状"，**必须先立现状基线**；行为保持或等价是验收红线。
> 触发入口在 `prompts/refactor.md` / `prompts/migrate.md`（一句话说清即进对应流程）。

### 10.1 存量重构（Refactoring / 重新设计）

**触发**：一句话"重构 XX" / "重新设计 XX" / "把 XX 模块重写"。

**红线**：**外部行为不变**（除非明确要求改行为——那部分按新需求走 §2）。

流程（六步）：

1. **现状基线先立（无基线不得动手）**：
   - 关键行为无测试 → **先补特征测试**（把现有行为锁死，不改断言，只记录行为）；
   - 记技术债清单（重复/坏味道/认知负荷点）→ `docs/02-design/refactor-baseline.md` 或并入 GAP；
   - **顺带扫"深化机会"**（外部参考：deep-modules 思路）——哪些接口该加深、哪些模块该拆、
     哪些概念该提炼成共享词汇；列出但**不承诺全部做**，作为重构候选池。
2. **目标态设计**：走 §3（选型/框架/数据），目标结构用 ADR 记录。
3. **行为保持承诺**：验收标准 = 原有测试 + 特征测试**全绿**；行为变化点显式列出并另走需求流程。
4. **增量落地**：小步重构，每步可提交可回滚；**大爆炸重写必须 ADR 论证**（为何无法增量）。
5. **回归验证**：新旧实现同输入同输出对拍，证据落 `docs/05-testing/`。
6. **收尾**：技术债清单逐项销号 + 复盘沉淀。

**Gate 适配**：Gate 0 前必做"现状基线"；Gate 4 加"行为对拍证据"；其余照常。
**裁剪**：单模块内小重构可合并 2–5，**但特征测试不可省**——没有测试锁行为，重构无法证明"没改坏"。

### 10.2 跨语言/跨框架迁移（Replatform）

**触发**：一句话"把 XX 从 go 迁到 java" / "从 python 迁移到 java" / "换框架"。

**红线**：**等价性**——同一输入 → 同一输出（含边界与错误路径）；对外接口契约不破。

流程（七步）：

1. **可行性评估（先于一切，不评估不开工）**：
   - 迁移理由（业务/性能/生态/人力）——**没有充分理由不迁**（换栈成本极高）；
   - 范围：全部还是部分？对外接口兼容要求？停机窗口？
   - 数据：库/存储怎么搬？存量数据量级？
   - 产出：`docs/01-requirements/migration-feasibility.md`（含决策记录）。
2. **目标架构（先查证，再设计——禁止 1:1 直译）**：
   - **① 查证目标语言的特性支持**：查官方文档与版本矩阵——并发模型、类型系统、生态库成熟度、
     性能特征、工具链；列出"目标栈能做到而原栈做不到"的能力清单。
   - **② 求证现状实现架构**：读懂现有代码的实际结构，标注其中**因原语言/框架限制而做的妥协**
     （手工状态管理、变通分层、缺失抽象、重复样板）。
   - **③ 重新设计目标架构**：让结构**充分利用目标语言/框架的现代化特性**；产出
     「原栈妥协点 → 新栈现代化做法」对照表，作为迁移的设计基线。
   - 产出：新栈选型（§3.1）+ 目标数据模型（CLM/PMD）+ 目标部署（§4）。
   - **红线**：把原架构原样翻译到新语言 = 迁移失败（"迁完还是老架构"）；确需保持原结构须 ADR 论证。
3. **契约冻结**：迁移期间对外接口契约**冻结**（interfaces.md）——"边搬边改"是事故源头。
4. **迁移策略 ADR 三选一**：

   | 策略 | 适用 | 说明 |
   |---|---|---|
   | **big-bang**（大爆炸切换） | 小系统/无并行可能 | 一次性切换，回退 = 旧版重启 |
   | **strangler-fig**（绞杀渐进） | 大系统/长周期 | 新旧并存，按业务边界逐个替换，流量逐步迁移 |
   | **parallel-run**（双轨对拍） | 高价值/高风险 | 新旧并行跑，同输入对拍输出，差异清零后切 |

5. **双轨对拍**：同一输入（历史流量回放/测试集）→ 新旧输出对比，证据入测试报告；**差异未清零不得切换**。
6. **数据搬迁**：ETL/DAS + 版本化迁移脚本 + **数据校验**（迁移后总量/抽样一致）+ 回退路径（见 configuration-management.md / change-management.md）。
7. **切换与回退**：走部署阶段；切换按 **M 级变更**（change-management.md §2）；切后观察期 + 回退预案**演练过**。

**Gate 适配**：Gate 0 前必做可行性评估；Gate 2 加"现代化特性利用对照表"；Gate 4 加"双轨对拍证据 + 数据校验报告"；Gate 5 加"回退演练记录"。
**红线**：等价性不满足时**禁止**以"先迁再改"蒙混——行为差异必须先按新需求走 §2，不能藏在迁移里。
