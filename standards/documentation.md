# 文档工程规范（Docs Engineering）

> 版本: 3.1.0 | 状态: active | 适用范围: 全部 Markdown 文档
> 回答三个问题：**docs 怎么编**（Obsidian/wiki 组织 + 头方式/索引/引用）、**每类文档为什么存在**
> （必要性）、**什么信息必须落 md**（落盘必要性）。
> v3.0 引入 **Obsidian 方式组织**：wikilink 交叉引用、每目录 index.md、FILE_INDEX 导航、
> 文档头/参考文档表/变更记录表三件套——让文档之间**互相可点、双向可达、无孤儿页**。
> v3.1 新增 **事实三分**（§3 首节）：先按事实性质分（现状快照/变更史/决策史），再按工艺阶段归档——
> 现状文档只写"现在是什么样"且**可整篇重写**，历史与决策各自另存，禁止混装。

---

## 1. Obsidian 方式组织（wiki 化，v3.0 新增）★

> 核心目标：**方便文档之间链接**。文档不是孤立的文件，而是可导航的 wiki。

### 1.1 交叉引用：wikilink 为主，相对链接为辅

| 引用类型 | 写法 | 说明 |
|---|---|---|
| **wikilink（首选）** | `[[target\|显示文本]]` | target 相对 `docs/` 根（不含 `.md` 后缀），显示文本可省略 |
| 章节锚点 | `[[target#标题\|显示]]` | 锚点对应标题必须存在 |
| 参考文档表 | `[[target\|docs/完整路径.md]]` | 文末参考表用双用途格式（显示=完整磁盘路径） |
| 同目录快捷 | `[[同目录文件名\|显示]]` | 也允许写相对路径 `[显示](文件名.md)` |
| 跨仓库 | 不建 wiki 链接 | 写 `见 <仓库>: <路径>`（跨仓禁止互相引用） |

**解析规则**（Obsidian 兼容）：`[[工程活动工艺全流程/设计/SAD-软件架构文档/SAD-agent-runtime]]`
= `docs/工程活动工艺全流程/设计/SAD-软件架构文档/SAD-agent-runtime.md`（若 docs 根不是仓库根，
按各项目 FILE_INDEX 声明的 wiki 根解析；默认 `docs/`）。

约束：

1. **禁止指向不存在的文件/标题**（写后即验，doc-check 校验 wikilink 目标存在）。
2. **禁止复制内容代替引用**——同一事实只存在一处（单一真源），其他文档用链接。
3. **双向可达**：被引用的文档应能从索引/上级文档找到（避免孤儿页）；每目录有 `index.md`。
4. 正式引用用 wikilink；反引号路径（`docs/xxx.md`）仅用于非导航性提及。

### 1.2 每目录 index.md（导航入口）

每个有文档的目录（阶段分册/子目录）维护一个 `index.md`（type: index）：

- **目录定位**：一句话说明本目录承载什么。
- **活动流**：本阶段子活动（mermaid 流程图或步骤表）。
- **交付物清单**：本目录全部文档的 wikilink 列表（`[[路径\|名称]]` + 一句话说明 + 状态）。
- **与上下游衔接**：上游/下游 index 的 wikilink。
- **变更记录**：版本/日期/变更（尾部）。

> index.md 是 wikilink 的"根"：新文档必须能被 index.md 或 FILE_INDEX.md 找到。
> 小目录（≤5 文件）允许以含交付物清单的 `README.md` 等效替代（如 `decisions/`）。

### 1.3 FILE_INDEX.md（全仓库导航唯一入口）

`docs/FILE_INDEX.md` 按分类段登记全部 `.md`（相对路径 + 一句话用途）：

```markdown
# FILE_INDEX - 文件索引
> 由 Agent 维护 | 最后更新: <YYYY-MM-DD> | 项目: <名称>

## 根目录（核心文档）      ← 根层：README/AGENTS/MEMORY 等
## docs/ 需求             ← 按阶段分册逐文件登记（含 wikilink）
## docs/ 设计
## ...（每阶段一段）
## standards/             ← 规范层
## prompts/ / scaffold/ / scripts/   ← 其他层
```

维护规则（强制）：

| 事件 | 动作 |
------|------|
| 新增文件 | 追加条目 + 在所属目录 index.md 加 wikilink |
| 删除/移动文件 | 移除/更新条目 + 更新所有引用方 + index.md |
| 目录改名 | 全仓库 wikilink 同步（doc-check 辅助） |
| 版本变更 | 更新"最后更新"日期 |

### 1.4 文档头三件套（Obsidian 惯例）

正式文档**头部**用元信息引用块：

```markdown
# 标题 — 一句话说明
> 版本: x.y.z | 创建: YYYY-MM-DD | 状态: Draft|Stable|Active
> 适用范围: (一句话)
> 关联: [[相关文档|显示名]] · [[另一篇|显示名]]
```

正式文档**尾部**两件套：

| 段 | 内容 |
|---|---|
| 参考文档表 | 本文引用的全部文档（wikilink 双用途格式） |
| 变更记录表 | 版本/日期/变更内容（倒序或正序，全项目统一） |

### 1.5 文档健康检查（Lint）

每 5-10 次会话或用户要求时执行（`scripts/doc-check.sh` 自动 + 人工抽检）：

| 检查项 | 方法 | 修复动作 |
|---|---|---|
| 断链/死 wikilink | 搜索 `[[...]]` 目标是否存在 | 更新或删除死链 |
| FILE_INDEX 遗漏 | `find docs/ -name "*.md"` 对比索引 | 补全遗漏文件 |
| index.md 遗漏 | 对比目录与 index 清单 | 补全 |
| 孤儿页面 | 检查未被任何文件引用的页面 | 添加交叉引用或删除 |
| 矛盾声明 | 对比原则文档与实现描述 | 标注或修正 |
| 占位符残留 | 搜 `{{...}}` | 模板外一律清除 |

## 2. 文档头方式（Frontmatter 规范）

### 2.1 适用规则

| 文档类型 | 是否必须 frontmatter | 说明 |
---------|:---:|------|
| 正式文档（标准/索引/模板/决策/报告/架构/计划/PRD/BRD/GAP/数据模型/运行手册） | ✅ 必须 | 见 §2.2 字段 |
| 流水账（进度日志/经验条目） | ❌ 不需要 | 文件名+标题即元数据 |
| 需求摄入（request.md） | ⚠️ 建议 | 至少保留"用户原话/提炼/假设表"三节结构 |

### 2.2 Frontmatter 字段（YAML，置于文件第一行 `---` 与 `---` 之间）

```yaml
---
title: <文档标题，与 # 标题一致>
type: index | standard | prd | reference | inventory | concept | spec | template | decision | guide | report | plan
tags: [tag1, tag2]                  # 可选，wiki 分类
status: draft | active | reviewed | superseded
version: <语义化版本，如 3.0.0>
date: <YYYY-MM-DD>
owner: <负责人/团队>
applies_to: <适用范围>               # standard/spec 类型必填
references:                          # 关联文档（wikilink target 或相对路径）
  - <关联文档>
---
```

约束：

1. `type` 必须是受控枚举（见上），避免自造类型；目录导航页一律 `type: index`。
2. `title` 与正文一级标题一致（单一真源）。
3. 模板文档用 `type: template`，占位符 `{{...}}` 允许存在。
4. 文档被新增/修改时，`date`/`version` 必须同步更新（同 FILE_INDEX 纪律）。

### 2.3 一级标题与段落结构

1. 每个文档**只能有一个一级标题**（`# `），其后为 `> 元信息引用块`（见 §1.4）。
2. 章节用二级标题（`## `）起，避免层级跳跃（禁止 `#` 后直接 `###`）。
3. 表格/列表前必须空行（CommonMark 渲染要求）。

### 2.4 正文编写九条（写作纪律）

> 约束**怎么写**（与 §2.2 格式、§2.3 结构互补）。九条来自企业体系文件的编写规范，
> 去组织化后按通用文档要求保留。**每条都可自查**。

| # | 条例 | 要求 | 反例 |
|---|---|---|---|
| **A** | **全貌完整、边界清晰** | 整体先系统规划，保证一致性与完整性；各域划分清晰，**避免重复、冗余、遗漏** | 两处写了同一规则且说法不同 |
| **B** | **遵循 5W1H** | 做什么/为什么/由谁做/何时做/何地做/如何做；过程类内容按 **PDCA**（策划-实施-检查-处置）组织 | 只写"做什么"，不说何时做、谁做 |
| **C** | **语言精简、前后一致** | 用书面语，避免口语化；**同类内容表述模式保持一致** | 同一概念一处叫"任务"一处叫"事项" |
| **D** | **角色统一、职责清晰** | 角色与职责定义与实际工作一致；**不新造角色**、界限不模糊；**及时调整历史遗留词汇** | 文档里出现已废弃的角色名 |
| **E** | **用词准确、避免歧义** | 慎用专有名词；**避免同词不同义**；指代统一；**同一术语不可多处解释**；新术语先查术语表 | `CMP` 既指配置文件清单又指配置管理过程 |
| **F** | **前后呼应、关联准确** | 避免"前有引用、后无应用"；文件间关联逻辑清晰，**避免频繁交叉关联或关联遗漏**；被引用的文档必须存在 | 正文说"见 §7"，但 §7 没有该内容 |
| **G** | **动宾搭配、标题醒目** | 子过程/任务定义**建议用动宾搭配**，用醒目标题理清主线 | 标题只写"流程""任务"两个字 |
| **H** | **裁剪/变更不容忽视** | 每个任务都要考虑不同场景下的**裁剪或变更**情况并明确定义 | 写死了唯一流程，小项目无法裁剪 |
| **I** | **交付前自查** | 提交评审前按检查清单完成自查（本项目 = 本规范 §7 健康检查 + Gate Review） | 把未自查的文档直接交出去 |

**强制条款**：

1. **E 条落地**：项目术语表 = `docs/glossary.md`；**新增术语必须先查、再登记**，禁止就地解释。
2. **F 条落地**：所有引用**必须**能被 `scripts/doc-check.sh` 校验（无断链）。
3. **H 条落地**：规范写"必须"处若允许裁剪，**必须**写明裁剪条件与降档方式
   （本项目统一做法：小任务可合并产物文件，但**内容不得消失**）。
4. **C/G 条落地**：同一文档内同类段落使用同一模板句式。

**修订记录写法**（配合 A/C 条）：

- 修改**必须**概括说明**修改要点**，且与后文实际改动一致；同类修改点可合并描述。
- 删除**必须**说明**删除原因**，并说明**是否有替代活动**。
- 修订记录**不能只写章节号**，须写**章节标题名称**，便于追溯。

## 3. 目录组织形式（Layout Blueprint）★

> 本文档是全仓库目录组织的**单一真源**；新增/移动目录必须先更新本蓝图再动文件。
> 归档前先过下方「事实三分」——**先定事实性质，再定目录**：目录回答"放哪"，性质回答"能不能放"。

### 事实三分（先定性质，再定目录）★

> 同一份文档只承载**一种性质**的事实。混装是现状文档腐化的头号原因：
> 读者必须读完一串变更记录才能还原"现在是什么样"，且文档一旦承载历史就再也不敢改。

| 事实性质 | 定义 | 典型文档 | 时间属性 |
|---|---|---|---|
| **现状快照** | 只描述"**当前对齐代码的真实情况**" | BRD · architecture/ODD · SAD/SAS · CLM/PMD · tech-selection · RUNBOOK · FILE_INDEX · glossary | **可整篇重写**（随代码演进被覆盖） |
| **变更史** | 只记录**真实发生过的变更操作** | CHANGELOG/CHP · 部署与切换记录 · `04-progress/` 日志 | **只增不改** |
| **决策史** | 只记录**真实做出的决策与理由** | ADR（`02-design/decisions/`）· 选型取舍段 | **只增不改**（由新 ADR supersede，不回头改写） |

**强制条款**：

1. **现状类文档禁止内嵌历史**——不写"之前是什么样/这次改了什么"；改了什么进变更史，为什么改进决策史。
   现状文档只回答"现在是什么样"。
2. **现状类文档必须能被整篇重写**：重写后不丢信息（历史已另存）。做不到 = 历史被塞进了现状。
3. **变更史与决策史只增不改**：写错了用追加更正，不改写旧条目。
4. **代码与运行实例是最终事实源**：现状文档与代码冲突时**以代码为准**并立即修正文档，
   禁止用文档"覆盖"代码事实（与 §4.1 落盘必要性、process.md §5 目标/差距分离配套）。

**工程活动工艺全流程的现状视图**（五段覆盖自检，用于核对"是否对齐当前代码"）：

| 段 | 必须回答 | 落到哪份现状文档 |
|---|---|---|
| 1 需求 | 需求编号 · 需求映射 | BRD + 需求追踪矩阵 |
| 2 架构 | 图文说明 · **可依据事实的**规划说明 | architecture.md/ODD · SAD/SAS |
| 3 验证 | 需求映射下的验证案例 · 验证数据集 · 验证工具；**严格覆盖全部需求**、求真务实 | FTR/NFTR + `05-testing/` 证据 |
| 4 交付 | 资源预估 · 运行环境 · **代码语言与版本** · 安装手册 | HRP · TTM · RUNBOOK 部署章 |
| 5 运维 | 产品使用说明 | RUNBOOK + README 使用说明 |

> 五段是**现状快照的覆盖清单**（读现有文档做自检），不是新建五份文档；缺哪段补哪段。

### 全仓目录蓝图（0X-* 分册制，与工艺阶段对应）

```text
<项目根>/
├── README.md / MANUAL.md      # 给人看：总览 + 使用手册
├── AGENTS.md / CLAUDE.md      # Agent 入口：协议 + 铁律
├── MEMORY.md                  # 状态/待办/硬约束（会话间继承）
├── LICENSE / .env.example / .gitignore
├── docs/                      # ★ 项目产出文档（按工艺分册，见下）
├── standards/                 # 规范层（可执行约束）
│   ├── README.md              # 规范地图（框架通用规范）
│   ├── *.md                   # 通用规范：安全/可靠性/性能/可观测/测试/风格/文档/工艺/接口
│   ├── languages/             # 语言适配：java/python/rust/go/node
│   └── enterprise/            # ★ 企业存量规范，见其 README
├── prompts/                   # 给用户的一句话指令模板
├── scripts/                   # 工具：init/cleanup/doc-check/quality-gate/journal/experience
└── scaffold/                  # 新项目模板（生成/转正用）
```

### docs/ 分册内容约束（0X-* 与工艺阶段映射）

| 分册 | 工艺阶段 | 允许内容类型 | 禁止放入 |
------|---------|-------------|---------|
| `00-request/` | 需求·澄清 | 用户原话、假设表、澄清记录 | 设计/代码内容 |
| `01-requirements/` | 需求·拆解映射 | BRD/GAP/TSP/FPE/WLE、需求追踪矩阵、变更记录 | 技术实现细节 |
| `02-design/` | 分析+设计 | PFA/SRS/DAS/FTP、ODD/SAD/SAS、ADR、CLM/PMD/ETL、tech-selection、PRT | 运行时状态 |
| `03-plan/` | 计划 | 任务计划、里程碑、DoD | 过程流水账（放 04） |
| `04-progress/` | 开发 | 进度日志 `YYYY-MM-DD*.md`（流水账，无 frontmatter） | 结论性文档 |
| `05-testing/` | 测试 | FTR/NFTR、测试计划、测试脚本子目录 | 开发过程记录 |
| `06-experience/` | 经验 | 经验条目 `YYYY-MM-DD*.md`、项目复盘 | 企业规范 |
| `07-ops/` | 部署+维护 | RUNBOOK/runbook.md、HRP/TTM/DRR/CTR、CHANGELOG、CMP、排障 | 开发文档 |
| `FILE_INDEX.md` / `README.md` / `glossary.md` / 各目录 `index.md` | 全仓/阶段 | 索引/总览/术语 | 主题内容 |

> **企业级项目可选中文阶段目录**（`docs/需求/`、`docs/分析/`、`docs/设计/`、`docs/开发/`、
> `docs/测试/`、`docs/部署/`、`docs/切换/`、`docs/管理/`），wiki 规则不变
> （index.md + wikilink + FILE_INDEX）。两种方案**选一种**，全仓库统一，禁止混用。
>
> **中文目录适用场景**：交付物需按工艺阶段归档、读者以中文为主、或与既有企业级项目保持一致时优选。
> 一旦选定即成为该项目的全局约定，**不得在项目内混用两套方案**（混用会让读者在两套体系间反复翻译）。

### 项目文档蓝图（中文阶段目录方案，通用）

任何项目（软件包、插件、服务、脚本工具集）都可套用以下结构；`docs/` 之外的文件是通用约定：

```text
<project>/
├── README.md / CHANGELOG.md / LICENSE     # 给人看：定位/能力/使用；变更史；许可
├── AGENTS.md / CLAUDE.md                  # Agent 入口：本项目的特有约束与铁律（可选但强烈推荐）
├── MEMORY.md                              # 状态/待办/硬约束（会话间继承，可选）
├── <源码与构建产物目录>                     # 按技术栈自定（src/、lib/、scripts/ 等）
└── docs/
    ├── README.md          # 阶段总览：八段闭环 + 阶段总览表 + 阅读路径
    ├── glossary.md        # 术语表（本项目专有术语；通用工艺术语引用本规范，不复制）
    ├── FILE_INDEX.md      # 全库导航（每文档一行含 wikilink）
    ├── 需求/  index.md + BRD-/TSP-/FPE-/WLE-/RVW-
    ├── 分析/  index.md + PFA-/SRS-/DAS-/FTP-/WTR-
    ├── 设计/  index.md + ODD-/SAD-/SAS-/CLM-/PMD-/ETL-/PRT- + decisions/(ADR-)
    ├── 开发/  index.md + CODE-
    ├── 测试/  index.md + FTR-/NFTR-
    ├── 部署/  index.md + HRP-/TTM-/DRR-（含 RUNBOOK）
    ├── 切换/  index.md + CTR-
    └── 管理/  index.md + PCH/PP/CMP/QAP/RMP/CHP/CMP2/PSR-
```

**按需填充**：八段是骨架，**只建实际有内容的段**（简单项目可能只有 `开发/` + `测试/`）；
但**已建的段必须带 `index.md`**，且 `docs/README.md` 的阶段总览表要如实标注哪几段为空。
不建空目录占位。

**根目录只留入口类文件**：`README.md`（人读）、`AGENTS.md`/`CLAUDE.md`（agent 读）、`CHANGELOG.md`、`LICENSE`、
`MEMORY.md`（可选）。**规范、手册、指南等主题文档一律进 `docs/` 对应段**——散在根目录会让读者无从判断哪份是权威、
也让"项目根"退化成杂物间。

**常见映射**（既有文档形态 → 标准位置）：

### 命名约束

1. 分册目录固定为 `0X-<英文名>`（00-request ~ 07-ops），禁止自造分册编号；新分册需 ADR 或用户确认。
2. **工艺交付物前缀**（与 process.md 术语表一致，方便 wiki 归类与搜索）：

| 前缀 | 交付物 | 前缀 | 交付物 |
|---|---|---|---|
| `BRD-` | 业务需求说明书 | `ODD-` | 总体设计说明书 |
| `GAP-` | 差距分析报告 | `SAD-` / `SAS-` | 软件/系统架构文档 |
| `TSP-` | 技术方案建议书 | `CLM-` / `PMD-` / `ETL-` | 数据/物理模型/ETL |
| `PFA-` / `SRS-` / `DAS-` / `FTP-` | 分析阶段四件套 | `FTR-` / `NFTR-` | 功能/非功能测试报告 |
| `ADR-` | 架构决策记录 | `RUNBOOK-` / `runbook` | 运行手册（维护指南） |
| `PRT-` | 性能风险跟踪表 | `HRP-` / `TTM-` / `DRR-` / `CTR-` | 部署/切换类 |
| `FPE-` / `WLE-` | 估算 | `RVW-` / `WTR-` | 评审/走查记录 |

3. 流水账文件名：`YYYY-MM-DD[-\<主题\>].md`（journal/experience 脚本自动生成）。
4. 禁止文件名含空格与 `/\:*?"<>|`；中文文件名允许但不与英文混用同一目录命名风格。

### 文档生成纪律（写每份文档前先过一遍）

> 这 8 条是**生成文档时的强制检查**，用于防止"写了很多、读者仍然不知道现在是什么样"。

1. **先定事实性质，再定目录**（事实三分，见前文）：这份文档是**现状快照**、**变更史**还是**决策史**？
   同一份文档只承载一种性质——混装是文档腐化的头号原因。
2. **现状类文档禁止内嵌历史**：不写"之前是什么样/这次改了什么"。
   改了什么进变更史（CHANGELOG/CHP），为什么改进决策史（ADR）。写完自检：**能不能整篇重写而不丢信息？**
   不能 = 历史被塞进了现状。
3. **每份文档必须回答"没有它会发生什么"**：答不上来就不建（见 §4 必要性论证）。
4. **索引与内容分离**：`README`/`index.md`/`FILE_INDEX.md`/`glossary.md` 只做导航与术语，
   **不放主题内容**；主题内容进对应段的交付物文件。
5. **交付物用标准前缀命名**（见前表）：`BRD-`/`SAD-`/`FTR-`/`PP-`/`RMP-` 等，
   让检索与归类不依赖记忆。**自造缩写 = 自造同义异名，禁止**。
6. **代码与运行实例是最终事实源**：文档与代码冲突时**以代码为准并立即修正文档**，
   禁止用文档"覆盖"代码事实。
7. **写完即验**：链接可达（相对路径按所在层级算）、frontmatter 齐全（§2.2）、
   与 `FILE_INDEX`/依赖矩阵同步（§5.2）、占位符已全部替换（模板变量不得残留）。
8. **移动/改名必须同批修链**：目录迁移与引用修复是**一件事，不是两步**——
   迁移后立刻全库扫引用（含 wikilink、相对链接、脚本文本提及），修完再提交。

> **反面清单（命中即返工）**：
> - 根目录散落主题文档（规范/手册/指南不在 `docs/` 对应段）
> - 同一项目内两套目录方案混用（如 `0X-*` 与中文阶段目录并存）
> - 建了空目录占位、或建了段却没有 `index.md`
> - 现状文档里出现"本次/之前/已改为"等时间叙事
> - 迁移了文件但没修引用（断链）

### 新增/移动目录规则

1. 先回答：新目录承载的内容是否已有归属分册？（对照上表）
2. 确需新增：更新本蓝图 + `docs/FILE_INDEX.md` + 依赖矩阵（§5.2）+ index.md，并在进度日志记录理由。
3. 目录改名：全仓库 wikilink 同步 + doc-check 验证 + 蓝图更新（一次完成，禁止分多次）。
4. **文档健康检查**：用 `doc-check` 类脚本扫断链与 frontmatter；把检查命令写进项目 README，
   让"文档是否健康"可复跑、不靠人肉看。

## 4. 文档必要性论证（每类文档为什么必须存在）

> 原则：**每份文档都必须回答"没有它会发生什么"**。答不上来的文档不建。

| 文档 | 必要性 | 没有它的后果 |
------|--------|-------------|
| `docs/00-request/request.md` | 需求唯一真源；假设与澄清留痕 | 范围漂移、误解无法追溯 |
| `docs/01-requirements/BRD-*.md` | 目标态 + 可测试验收标准（DoD 依据） | 无法验收、开发凭感觉 |
| `docs/01-requirements/GAP-*.md` | 现状快照 + 差距 delta | 现状问题混入目标文档、无法评估改进 |
| `docs/02-design/tech-selection.md`/ADR | 技术选型理由留痕 | 选型反复、后人不知道为什么 |
| `docs/02-design/architecture.md`（ODD） | 模块边界与契约总览 | 模块耦合失控、新人无法理解 |
| `docs/02-design/CLM-*.md` + `PMD-*.md` | 数据模型与 DDL 基线 | 建表凭感觉、迁移不可控 |
| `docs/02-design/decisions/adr-*.md` | 决策背景与备选存档 | 决策反复、后人不知道为什么 |
| `docs/03-plan/tasks.md` | 里程碑/任务/DoD/依赖 | 进度不可跟踪、批次不可验证 |
| `docs/04-progress/*.md` | 诚实过程记录（含失败） | 无法复盘、跨会话失去连续性 |
| `docs/05-testing/*.md` | 测试证据（真实命令输出） | "完成"无法证明 |
| `docs/06-experience/*.md` | 经验沉淀与跨项目继承 | 重蹈覆辙 |
| `docs/07-ops/runbook.md` | 部署/排障/回滚手册（维护指南） | 无法运维、交接困难 |
| `docs/FILE_INDEX.md` + 各 `index.md` | 全仓库/阶段导航 | 文档不可发现、索引腐烂 |
| `docs/glossary.md` | 术语统一 | 沟通歧义、语义漂移 |
| `standards/*.md` | 生产级底线（可执行检查项） | 质量随 Agent 状态波动 |
| `MEMORY.md` | 当前状态/待办/硬约束 | 新会话不知道做到哪、什么不能碰 |

### 4.1 什么信息**必须**落 md（落盘必要性）

以下信息**禁止只存在于对话/聊天/代码注释**中，必须落盘：

1. **需求与假设**：用户原话、Agent 做的假设、澄清结论。
2. **决策与理由**：技术选型、架构取舍、数据模型决策（含为什么）。
3. **过程事实**：做了什么、验证命令与结果、失败与回退。
4. **经验教训**：踩坑、根因、解决、适用范围。
5. **状态与约束**：当前进度、待办、硬性规定、凭证策略。
6. **契约与接口**：模块接口、API 语义、数据结构、错误码。
7. **验收证据**：测试输出、基准数据、评审结论。

### 4.2 为什么必须落 md（跨会话继承的根因）

| 理由 | 说明 |
------|------|
| **上下文有界** | AI 会话上下文有限，md 是跨会话、跨 Agent 的记忆载体 |
| **可追溯** | 一句话需求 → 澄清 → 拆解 → 映射 → 决策 → 代码 → 证据，全链可回溯 |
| **可审查** | 企业交付要求文档评审、审计、交接 |
| **防幻觉** | 文档与实现对照，宣称必须有证据 |
| **并行协作** | 多 Agent/多人共享单一真源，避免各自脑补 |

## 5. 交叉引用约束（相互引用规范）

### 5.1 引用方式（v3.0 更新）

| 引用类型 | 写法 | 要求 |
---------|------|------|
| 同仓文件（wiki） | `[[路径/文件名\|显示]]` | 目标必须存在（doc-check 校验 wikilink） |
| 同仓文件（fallback） | `[显示](相对路径.md)` | 路径必须真实存在 |
| 锚点引用 | `[[文件#标题\|显示]]` / `[文本](file.md#标题)` | 锚点对应标题必须存在 |
| 反引号路径 | `` `docs/xxx.md` `` | 仅用于非导航性提及 |
| 外部链接 | `https://...` | 说明引用理由 |

### 5.2 依赖矩阵（必更新项 vs 审查项）

任何文件变更后，按矩阵决定联动更新范围：

| 被变更文件 | 必更新（依赖方） | 审查项（相关方） |
-----------|-----------------|-----------------|
| `AGENTS.md`（铁律/流程） | `MEMORY.md`、`docs/FILE_INDEX.md`、项目级 `AGENTS.md` 模板 | `standards/` 相关规范 |
| `standards/*.md` | `standards/README.md` 地图、FILE_INDEX | `AGENTS.md` 铁律引用 |
| `docs/FILE_INDEX.md` | 无 | 所有被索引文档 |
| 各目录 `index.md` | FILE_INDEX、被列文档的反向可达 | 上游/下游 index |
| 架构决策（ADR） | `docs/02-design/decisions/README.md` 索引、FILE_INDEX | `architecture.md`、AGENTS.md |
| BRD/GAP 变更 | 需求追踪矩阵、验收标准引用方、FTR 追溯 | 分析/设计文档 |
| 数据模型（CLM/PMD） | 迁移脚本、FTR、接口文档 | 需求矩阵 |
| 代码模块/接口 | 对应 `standards/interfaces.md` 契约记录、API 文档 | 测试文档、README |
| 环境变量/配置 | `.env.example`、运行手册（docs/07-ops/） | MEMORY.md 状态表 |

### 5.3 引用纪律

1. **禁止指向不存在的文件/标题**（写后即验，doc-check 兜底）。
2. **禁止复制内容代替引用**——同一事实只存在一处（单一真源），其他文档用链接。
3. 文档间双向可达：被引用的文档应能从索引/上级文档找到（避免孤儿页）。
4. 模板中允许 `{{...}}` 占位符，正式文档禁止残留。

## 6. 文档依赖链（工艺对应关系）

```
一句话需求
   │
   ▼
docs/00-request/request.md ──► docs/01-requirements/BRD-*.md + GAP-*.md
                                      │
                                      ▼
                          docs/02-design/tech-selection + ADR
                          docs/02-design/architecture.md（ODD/SAD/SAS）
                          docs/02-design/CLM-*/PMD-*/ETL-*（数据设计）
                                      │
                                      ▼
                                docs/03-plan/tasks.md
                                      │
              ┌───────────────────────┼───────────────────────┐
              ▼                       ▼                       ▼
       docs/04-progress/        src/（代码）           docs/05-testing/
       （每批诚实记录）              │                   （证据报告）
                                      ▼
                         docs/06-experience/ + MEMORY.md（经验与状态回流）
                                      ▼
                       docs/07-ops/runbook.md + README（交付：部署/维护指南）
```

依赖规则：

1. 下游文档引用上游文档的**编号/版本**，不复制内容（如 BRD 引用 request.md 假设编号）。
2. 变更只能顺流传播：改需求 → 评估 BRD/架构/数据模型/计划/测试/运行手册是否联动（见 §5.2 矩阵）。
3. 流水账（progress/experience）是过程的**唯一事实源**，复盘报告引用它，禁止凭记忆重写。
